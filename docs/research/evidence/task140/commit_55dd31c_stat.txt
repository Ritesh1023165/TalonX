    feat(ingest): Task 140 B1/B4/B5 -- DIGEST delivery off by default, explicit opt-in
    
    Routine filing-inventory digests were still reaching Telegram by default
    under Task 138's policy (a non-substantive event routed to DIGEST, not
    DASHBOARD_ONLY, and the periodic DIGEST message itself was always sent).
    Per the explicit product goal: moving noise into a smaller bundle is
    still noise if the bundle itself was never requested.
    
    talonx_ingest/intelligence/service/config.py: new
    ServiceConfig.deliver_digest_enabled (env TALONX_INTEL_DELIVER_DIGEST_
    ENABLED), default False -- independent of the existing
    deliver_intelligence_cards/TALONX_INTEL_DELIVER_CARDS master switch,
    which continues to govern IMMEDIATE alone.
    
    talonx_ingest/intelligence/service/runner.py: deliver_cycle computes a
    separate digest_mode (forced "disabled" whenever deliver_digest_enabled
    is False, regardless of the overall IMMEDIATE mode) and passes it to
    process_digest -- reuses process_digest's OWN existing mode="disabled"
    branch (rows stay PENDING, logged HELD/"delivery disabled", nothing
    sent, nothing lost, nothing mutated) rather than a new delivery engine
    or a one-time reclassification batch. Because this check runs on EVERY
    deliver_cycle call, not once at cutover, no backlog row -- old or new --
    can ever bypass the new default by outliving a batch job; it is held on
    every single cycle it is evaluated.
    
    9 new tests in tests/test_task117_delivery_runner_integration.py:
    default-off holds a fresh DIGEST row while IMMEDIATE is unaffected;
    explicit opt-in sends the aggregated digest exactly as before;
    durability across 3 repeated cycles (the same row never escapes).
    
    docs/research/NOTIFICATION_POLICY.md Sec 2.1: documents the new default
    and how it was verified reaching the running process.
