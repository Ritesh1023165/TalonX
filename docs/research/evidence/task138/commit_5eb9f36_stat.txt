    feat(dispatch,ingest): Task 138 Workstream 3 -- reply "details" for informational alerts
    
    Implements deterministic, durable reply-for-details correlation for
    Intelligence informational cards through the existing (single) Original
    TelegramReplyListener -- no external LLM, no new process, no new
    schema.
    
    - talonx_ingest/intelligence/delivery/reply_correlation.py (new):
      correlates an inbound Telegram reply (chat identity already enforced
      upstream; Telegram message ID) against the durable
      `intelligence_delivery` table, reusing its existing
      `transport_message_id` column. A single-card send stores the bare
      numeric id; a digest send stores `digest:<digest_id>:<message_id>`
      across every constituent row -- one SQL query resolves both, so one
      Telegram message can map to multiple events. Returns a compact
      indexed summary for a multi-event message, or full facts (accession,
      filing link, source-accepted/enqueued/sent timestamps, persisted
      significance reasons, the original card text with HTML markup
      stripped for this plain-text reply) for one. Old messages predating
      this feature get a truthful "can't identify, won't guess" response,
      never a guess. Production wiring
      (`build_intelligence_details_resolver`) opens a read-only
      (file:...?mode=ro) handle to Intelligence's own ingestion_ledger.db,
      mirroring talonx_signals/reply.py's established
      build_experimental_dxre_resolver contract exactly, including graceful
      (None, None) on any construction failure.
    
    - talonx_dispatch/telegram_listener.py: new `message_resolvers` ordered
      list (Message -> str | None), tried BEFORE the existing
      `extra_resolvers` (str -> str | None) -- receives the full inbound
      Message so a resolver can read reply_to_message.message_id for true
      message-ID correlation, which extra_resolvers' text-only contract
      cannot. Empty by default (byte-identical when unused). Its reply is
      sent with plain=True (parse_mode=None): resolver output can carry
      arbitrary, uncontrolled SEC-sourced text not guaranteed Markdown-safe,
      and sending it under the default MARKDOWN parse mode risked a
      Telegram "can't parse entities" send failure.
    
    - talonx_dispatch/consumer.py: DispatchAgent gains a passthrough
      `message_resolvers` constructor param.
    
    - run_talonx.py: registers build_intelligence_details_resolver's
      resolver into the single DispatchAgent alongside the existing
      Experimental D/X/R/E resolver (same read-only, no-second-poller
      posture); closes the reader handle in the existing shutdown `finally`
      block alongside exp_reply_store.
